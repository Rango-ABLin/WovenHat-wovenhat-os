# WovenHat OS — Audit (2026-09-04)

Scope: static review of `kernel/` (18.7k lines of Rust across 33 files) and
`docs/`. No compiler was available in the review environment (no `rustc`,
`rustup`, or network access to `static.rust-lang.org`), so nothing here was
verified by an actual build — treat the code-level findings as reviewed by
eye and confirmed against the exact crate API used (`x86_64` 0.15.5 source
was fetched from crates.io to confirm `RdRand`'s signature before it was
used, see below), but **run `cargo clippy --workspace -- -D warnings` and
the QEMU boot self-tests before trusting this in CI.**

## 1. What's actually in better shape than the repo's own docs claim

`docs/wovenhat-os-master-roadmap.md` (checked in, dated "September 2026")
states networking is "Absent" and that guard pages were "mentioned in an
earlier roadmap doc but not found implemented." Neither is true of the code
as it stands:

- **Networking exists and is substantial**: `virtio_net.rs` (virtio-net
  transport) + `network.rs` (smoltcp integration) implement DHCP, DNS,
  ICMP ping, and UDP/TCP sockets exposed through a syscall ABI, gated by a
  dedicated capability. This is Phase A4 from the roadmap, already mostly
  built.
- **Stack guard pages exist**: `userspace.rs`'s `UserStack` tracks a
  `guard_base` and the boot self-tests explicitly assert unmapped stack
  guards (`main.rs`, "independent user roots, unmapped stack guards, and
  RW/NX stacks verified").
- **`sys_mmap` cannot create W^X mappings**: `userspace::map_anonymous`
  hard-codes the executable flag to `false` for every anonymous mapping
  (`paging::map_user_range_in(..., writable, false)`), and the mmap
  syscall only ever exposes a writable bit, never an executable one. The
  roadmap's claim that "nothing stops a process from mapping
  writable+executable memory post-load" does not match current code.

**Takeaway**: the project is moving faster than its own planning docs.
That's a good problem to have, but it means anyone (human or AI) reading
`docs/*roadmap*.md` cold will plan against a stale picture of the system
and duplicate work that's already done, or worse, "fix" things that aren't
broken. See §4.

## 2. Real finding, fixed in this pass: predictable network entropy

`network.rs` seeded smoltcp's `Config::random_seed` — which feeds TCP
initial sequence number generation and other internal randomized choices —
with a fixed compile-time constant (`0x5748_4f53_4e45_5435`, i.e. an ASCII
easter egg spelling "WOSNET5"). That means **every boot of every WovenHat
instance produced the same TCP sequence-number stream**, which is exactly
the condition that makes TCP session hijacking / off-path spoofing
attacks practical against a stack that would otherwise resist them.

Notably, `hal/cpu.rs` already detects RDRAND support at boot
(`CpuFeatures::has_rdrand`) and prints it, but nothing in the kernel
actually *called* the instruction anywhere.

**Fix applied** (`kernel/src/entropy.rs`, new file):
- `entropy::random_u64()` tries hardware RDRAND (via
  `x86_64::instructions::random::RdRand`, already a transitive dependency)
  up to 8 times, since RDRAND is documented to occasionally fail to
  produce a value under load.
- Falls back to a SplitMix64 mix of the monotonic timer tick count and a
  stack address if RDRAND is absent or exhausts its retries — explicitly
  documented as *not* cryptographically secure, only better than a static
  constant, and unsuitable for future key-material use.
- `network.rs` now calls `entropy::random_u64()` instead of the literal.

This is deliberately the only behavioral change made in this pass: it's
small, self-contained, doesn't touch scheduling/paging/locking (SMP-
sensitive code that the roadmap itself flags as needing a full lock audit
before touching), and is easy to review line-by-line without a compiler
on hand.

## 3. Confirmed still-open gaps (matches roadmap, independently verified)

- **No ASLR.** `grep -rin "aslr" kernel/src` finds nothing outside the
  roadmap doc itself. `entropy.rs` now gives you a real random source to
  build this on top of — randomizing `mapping_start` in the ELF loader and
  the anonymous-mmap base per process is the natural next step and no
  longer blocked on "we have no RNG."
- **Coarse-grained capabilities.** `capability.rs` gates `FileRead` /
  `FileWrite` per-process, not per-file — a process with `FileWrite` can
  write any file it can open, not just files it was granted.
- **Docs sprawl.** `docs/` has 38 files, 15 of which are narrow
  `STAGE9-*-FIX.md` incident write-ups. Worth consolidating into a
  changelog rather than leaving them as free-floating top-level docs that
  compete with the roadmap for "source of truth" status.
- **Code hygiene is otherwise good**: 173 `unsafe` blocks (expected for a
  kernel; each one is small and locally scoped, not a handful of giant
  unsafe regions), only 7 `.unwrap()`/`.expect()` calls in 18.7k lines, and
  zero `TODO`/`FIXME`/`XXX` markers — the last of these cuts both ways
  (disciplined, or under-documented known gaps; the roadmap doc is
  apparently where gaps get tracked instead).

## 4. Process recommendation, not just a code one

Keep exactly one live roadmap document. The repo currently has
`os-improvement-roadmap.md`, `COMPLETE-AI-DIRECTIVE.md`,
`next-steps-implementation.md`, `more-steps.md`, `ten-steps.md`, and
`wovenhat-os-master-roadmap.md` (the last explicitly says it supersedes
the first two, but the first two are still checked in). Every one of
these will drift out of sync with the code at the pace this project is
moving. Delete or archive the superseded ones in the same PR that lands
any milestone work, not as a separate cleanup that never happens.
